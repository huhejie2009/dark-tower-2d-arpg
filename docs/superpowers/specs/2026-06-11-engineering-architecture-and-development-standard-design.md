# 工程架构与开发规范设计

日期：2026-06-11  
状态：已完成逐节确认，待落地执行  
适用项目：Dark Tower 2D ARPG

## 1. 目标

本规范用于约束项目后续设计、编码、测试和维护工作，目标如下：

- 明确模块、系统、类和场景节点的职责边界。
- 保持核心玩法规则可测试、可组合、可扩展。
- 采用务实的面向对象设计，避免庞大继承树和无意义抽象。
- 控制脚本规模、依赖方向与技术债增长。
- 将性能、存档安全和回归测试纳入功能完成标准。
- 支持自动战斗与手动操作共享同一套战斗和 Build 规则。

本项目采用“新代码强制执行、旧代码触碰即迁移”的渐进式治理方式。现有大型脚本登记为技术债，不要求一次性重构，但不得继续增加不属于其既有职责的新功能。

## 2. 架构方案

项目采用模块化单体架构，并在运行时实体中使用组件化设计。

不采用以下极端方案：

- 不把所有规则都实现为场景 Node，避免无意义的节点和信号开销。
- 不建立完整且沉重的领域驱动框架，避免降低当前迭代速度。
- 不为了形式上的面向对象，把纯函数和无状态规则包装成复杂对象层级。

对象选择原则：

| 问题类型 | 推荐实现 |
| --- | --- |
| 有身份、状态和生命周期 | 对象或 Node |
| 可组合的运行时能力 | 组件 Node 或 RefCounted 对象 |
| 静态游戏配置 | 只读 Resource |
| 纯公式、校验和转换 | 无状态规则对象或静态函数 |
| 跨层数据传输 | 明确 DTO 或只读快照 |
| 一次业务操作的结果 | OperationResult |

## 3. 总体分层

依赖方向如下：

```text
App / Scene
     |
     v
UI --> Application
          |
          v
        Domain
          ^
          |
   Infrastructure
```

上层可以依赖下层，下层不得依赖上层。禁止循环依赖。

| 层级 | 职责 | 允许依赖 |
| --- | --- | --- |
| App / Scene | 场景组装、顶层流程、场景切换 | Application、Actors、UI、Infrastructure |
| UI / Presentation | 展示 ViewModel、转译输入、视觉反馈 | Application、只读 DTO、表现资源 |
| Application | 编排完整业务用例和事务 | Domain、Infrastructure 接口 |
| Domain | 战斗、技能、装备、掉落、成长核心规则 | Domain 基础类型、Shared |
| Actors | 玩家、敌人、投射物等运行时实体 | Domain、运行时组件 |
| Infrastructure | 存档、资源读取、日志、平台能力 | Domain 数据契约、Shared |
| Shared | 结果类型、通用值对象和基础工具 | 不依赖业务模块 |

## 4. 系统职责

| 系统 | 负责 | 禁止负责 |
| --- | --- | --- |
| 场景流程 | 进入楼层、清层、死亡、回城和场景切换 | 伤害公式、装备计算、UI 绘制 |
| 战斗 | 攻击请求、命中、伤害、暴击和状态效果 | 存档、掉落界面、职业成长 |
| 技能 | 技能定义、释放条件、冷却、消耗和触发链 | 寻路、界面按钮、直接写存档 |
| 自动战斗 | 目标选择、移动意图、技能优先级 | 修改技能规则、提供挂机数值加成 |
| 装备 | 槽位、穿脱、词条汇总和宝石孔 | 生成 UI、直接保存文件 |
| 掉落 | 掉落池、稀有度、词条生成和物品实例 | 自动穿戴、决定 UI 推荐文案 |
| 背包 | 容量、堆叠、锁定、收藏和废品操作 | 装备数值公式、商店定价 |
| 天赋成长 | 节点解锁、前置条件、等级和属性修正 | 技能表现、场景节点操作 |
| 角色属性 | 汇总基础、装备、天赋和状态修正 | 保存文件、读取 UI |
| AI | 感知、决策和行为意图 | 伤害结算、掉落生成 |
| UI | 展示 ViewModel、发送用户命令 | 直接修改领域数据或存档 |
| 存档 | 版本迁移、校验、原子写入和备份恢复 | 奖励计算、战斗判断 |
| 资源配置 | 加载技能、敌人、装备和关卡定义 | 保存玩家运行状态 |
| 音画表现 | 动画、特效、音效和受击反馈 | 决定命中、暴击和伤害结果 |

## 5. 运行时实体设计

采用组合优先。玩家、普通敌人和 Boss 不建立深层继承树。

```text
Actor2D
  HealthComponent
  AttributeComponent
  MovementComponent
  SkillCasterComponent
  StatusEffectComponent
  ActorPresentation
```

`Player2D` 和 `Enemy2D` 最终只负责组件装配、生命周期协调和场景接口。Boss 差异由行为组件、技能配置和阶段控制器表达。

组件规则：

- 一个组件只管理一种稳定能力。
- 组件不得直接查找 HUD、背包或存档对象。
- 组件之间通过明确接口、信号或协调器通信。
- 高频组件避免每帧创建 Dictionary 和临时数组。
- 可脱离场景树运行的规则不得依赖 Node。

## 6. 战斗与控制模式

自动模式和手动模式只改变施法请求的来源，不改变技能规则。

```text
InputController / AutoCombatController
  -> CastSkillUseCase
  -> SkillCasterComponent
  -> SkillRule + TriggerRule
  -> DamageResolver
  -> ProjectileSpawner
  -> CombatEvent
  -> Presentation
```

寒冰射击 CoC 等 Build 必须遵守以下原则：

- 手动和自动模式使用相同暴击率、冷却、触发限制和伤害公式。
- 自动战斗不得获得隐藏命中、伤害或触发加成。
- 表现层可以延迟或合并视觉事件，但不得改变战斗结果。
- 触发链必须有深度、冷却或来源限制，防止无限递归。
- 随机数来源必须可注入或可设置种子，以支持确定性测试。

## 7. 数据与接口

### 7.1 可变数据

- 一个可变状态必须有唯一所有者。
- 跨模块默认传递深拷贝快照、只读 DTO 或明确命令。
- UI 不得持有并任意修改玩家内部 Dictionary。
- 服务不得在未声明的情况下修改传入参数。
- 修改型方法应通过名称、返回值和文档明确表达副作用。

### 7.2 OperationResult

可能失败的业务操作统一返回结果对象，至少包含：

```text
is_success
error_code
message
data
```

适用操作包括穿戴、卸下、出售、分解、镶嵌、升级技能、进入楼层和保存。

### 7.3 ID 与配置

- 禁止散落裸字符串作为技能、词条、槽位和错误码。
- 稳定 ID 集中定义，或由强类型 Resource 提供。
- 显示名称与内部 ID 分离。
- 存档只记录稳定 ID，不保存 NodePath、脚本路径或运行时对象引用。

## 8. Godot 编码规范

### 8.1 命名

- 文件和类：`PascalCase`。
- 方法、变量和信号：`snake_case`。
- 常量：`UPPER_SNAKE_CASE`。
- 布尔值：使用 `is_`、`has_`、`can_` 或 `should_` 前缀。
- 公共方法使用业务意图命名，例如 `equip_item()`，禁止 `handle_data()` 等模糊名称。
- 测试文件使用 `regression_<behavior>.gd`。

### 8.2 类型

- 所有公共方法参数和返回值必须声明类型。
- 公共信号参数必须声明类型。
- 可确定类型的成员变量必须声明类型。
- Variant 和 Dictionary 只能用于确实需要动态结构的边界。
- 核心领域对象新增代码优先使用明确类型和值对象。

### 8.3 代码组织

- 一个文件只承担一个主要职责。
- 组合优先于继承。
- 继承用于真正的“是一个”关系，不用于复用少量工具方法。
- 注释解释原因、约束和非显然风险，不复述代码。
- 禁止魔法数字；玩法参数进入规则或配置。
- 禁止在业务代码中静默吞掉错误。
- 信号连接必须有明确生命周期，并防止重复连接。

### 8.4 规模门禁

| 项目 | 建议值 | 硬上限 |
| --- | ---: | ---: |
| 普通脚本 | 200 行 | 350 行 |
| 场景协调器 | 300 行 | 500 行 |
| 单个方法 | 25 行 | 50 行 |
| 方法参数 | 4 个 | 6 个 |
| 继承深度 | 2 层 | 3 层 |
| 单个 Node 的业务组件 | 6 个 | 10 个 |

超过建议值必须检查职责；新增代码超过硬上限时禁止合并，除非存在正式例外记录。

## 9. 依赖禁令

- Domain 不得引用 Node、Control、SceneTree、场景文件或存档 API。
- UI 不得直接引用或调用 SaveManager。
- Domain 和 Rules 不得引用 UI、App、Actors。
- 实体不得直接查找 HUD、背包窗口或主城页面。
- 禁止用字符串节点路径充当跨模块业务接口。
- 禁止一个模块直接修改另一个模块拥有的可变 Dictionary。
- 禁止跨层 Autoload 作为通用服务定位器。
- 禁止新增循环 preload 或循环 class_name 依赖。
- Infrastructure 不得决定玩法结果。

## 10. 性能规范

### 10.1 高频路径

`_process()` 和 `_physics_process()` 中禁止：

- 文件读写。
- JSON 解析。
- 同步资源加载。
- 全场景树搜索。
- 动态节点路径查找。
- 装备和天赋属性全量重算。
- 无必要的大数组、Dictionary 和字符串创建。

### 10.2 运行时策略

- 投射物、伤害数字、短时特效和高频掉落表现使用对象池。
- 属性系统采用脏标记，在源数据变化后集中重算。
- AI 使用分帧调度；远离玩家的单位降低决策频率。
- 配置和资源必须预加载或缓存。
- 大量相同事件可批处理，但不得改变玩法顺序和结果。
- 视觉层不得反向驱动权威战斗状态。
- 对象释放前必须断开外部信号或确保连接目标生命周期安全。

### 10.3 性能基线

当前目标基线：

- 1920x1080。
- 稳定目标 60 FPS。
- 普通楼层至少支持 80 个活跃敌人。
- 至少支持 150 个活跃投射物。
- 不出现持续增长的 Node、Object 或资源占用。

新增高频系统必须提供压力测试、基准场景或可重复的性能采样步骤。后续若目标硬件确定，应补充最低配置及帧时间预算。

## 11. 安全与存档规范

### 11.1 信任边界

所有存档、外部配置、命令行参数和插件输入都视为不可信数据。

必须验证：

- Variant 实际类型。
- 数值上下限。
- 枚举和稳定 ID。
- 字符串最大长度。
- 数组和 Dictionary 最大元素数。
- 浮点值是否为有限数。
- 物品实例 ID 是否有效且唯一。

### 11.2 存档安全

- 使用临时文件写入、重新校验、原子替换和备份恢复。
- 保存失败必须可观察，不得假装成功。
- 迁移只允许向前，并保留旧版本兼容测试。
- 未知字段按明确策略保留或丢弃，不得随机透传危险结构。
- 测试必须使用内存或临时存档，禁止写入真实玩家存档。
- 穿脱、出售、分解和镶嵌必须具备事务性，失败时不得丢物品。
- 奖励数量、货币、等级、层数和属性必须限制范围。

### 11.3 禁止行为

- 禁止根据存档内容动态加载任意脚本、场景或文件。
- 禁止执行来自玩家输入或存档的表达式。
- 禁止将真实本地路径、令牌或敏感日志写入发布存档。
- 发布版必须关闭测试后门、调试入口和不必要的详细日志。

本项目是单机游戏，无法彻底阻止玩家修改本地存档。安全目标是防止崩溃、数据破坏、越界资源加载和意外执行，而不是宣称存档不可篡改。

## 12. 测试与完成定义

### 12.1 测试层级

1. Domain 单元测试：公式、规则、边界和确定性随机。
2. Application 用例测试：完整业务操作及失败回滚。
3. Scene 集成测试：节点生命周期、信号和场景桥接。
4. Save 兼容测试：规范化、迁移、损坏数据和原子写入。
5. Regression 回归测试：历史行为和缺陷保护。
6. Performance 测试：高频系统的稳定帧时间和对象数量。
7. Manual QA：操作体验、可读性和长时间运行。

### 12.2 功能完成门禁

每项功能至少完成：

```text
确认职责归属
-> 编写失败测试
-> 实现最小功能
-> 相关回归
-> 场景烟测
-> 完整回归
-> 更新设计、进度或技术债记录
```

以下情况禁止合并：

- 任意 P0 测试失败。
- 真实存档可能被测试覆盖。
- 新增循环依赖或违反依赖方向。
- 新增脚本无例外地超过硬上限。
- 存在已知物品丢失或重复风险。
- 高频功能没有可重复验证方式。
- 主项目 headless 启动失败。

## 13. 遗留代码迁移

### 13.1 优先顺序

1. `Game2D.gd`
   - 拆出楼层流程、场景建造、奖励结算和菜单协调器。
   - 最终只保留场景组装与顶层协调。

2. `InventoryEquipmentWindow.gd`
   - 拆出背包、装备、详情、筛选和技能树控制器。
   - UI 通过 Application 用例修改数据。

3. `Enemy2D.gd`
   - 拆出动画表现、名称条、攻击、Boss 技能和行为组件。

4. `Player2D.gd`
   - 拆出动画、属性、受伤和技能释放组件。

5. 存档系统
   - 增加原子写入、备份恢复、严格范围验证和版本迁移。

### 13.2 迁移方法

- 不为达成行数指标机械拆文件。
- 每次只迁移一个明确职责。
- 先补行为测试，再移动实现。
- 迁移期间保留最薄的旧接口适配层。
- 调用方迁移完成后再删除适配层。
- 每次迁移运行相关测试、完整回归和场景烟测。
- 不顺手修改无关模块。

## 14. 自动化治理

后续应增加工程规范检查脚本，至少检查：

- 新增或修改脚本的规模上限。
- 禁止的跨层 preload 和依赖方向。
- UI 是否直接引用存档层。
- Domain 是否引用 Node、Control、SceneTree 或场景路径。
- 回归测试是否可能写入真实存档。
- 是否存在危险动态加载或表达式执行。
- 新增领域或应用系统是否具有对应测试。

自动检查应区分：

- 新增违规：立即阻断。
- 已登记遗留违规：允许存在，但不得恶化。
- 已触碰遗留模块：要求减少或至少不增加违规数量。

## 15. 例外流程

规范允许必要例外，但不得无声绕过。例外记录必须包含：

- 违反的具体规则。
- 无法遵循的技术原因。
- 风险和影响范围。
- 测试与保护措施。
- 负责人。
- 清理条件或目标阶段。

以下例外不得批准：

- 自动测试写入真实玩家存档。
- 从存档加载任意脚本或文件。
- UI 直接修改存档文件。
- 已知物品丢失或复制风险。
- P0 回归失败。
- 无边界的全局管理器继续增加职责。

## 16. 后续执行承诺

规范落地后，后续开发必须：

- 开始实现前确认功能归属和依赖方向。
- 优先复用已有领域接口，不复制规则。
- 对触碰到的遗留职责进行小步迁移。
- 不为形式上的面向对象滥用继承和抽象。
- 把性能、安全和测试作为完成条件。
- 需求与规范冲突时先明确风险和调整方案。
- 重要变更同步更新设计、进度和技术债文档。
